## Important interpretation

The missing-object *fresh clone failure* cannot be exercised against GitHub for this branch because GitHub rejects the dangling pointer before it becomes reachable. This is a protective server-side integrity check, not evidence that `jj` uploads LFS data. The successful retry required an explicit `git lfs push --object-id`; the subsequent fresh clone demonstrates recovery after that upload. Only 7,168 payload bytes were uploaded to the private GitHub LFS endpoint. No quota error occurred in these transport calls; the separate initial Windows runner unavailability is recorded elsewhere.

The temporary `git.ignore-filters=[]` snapshot also picked up the already hydrated `payload.bin` as raw bytes on its first pass. Replacing that disk file with its existing committed pointer and snapshotting again removed the unintended change before push. The pushed `jj diff --stat` contained only `.gitattributes` and `missing.bin`. This demonstrates why publishing a new pointer from `jj` needs explicit verification of *all* LFS paths in the exported commit.

The second `jj git push` emitted `Updated signatures of 1 commits`, so its local candidate commit ID changed during publication. The final remote SHA above is authoritative.

## Limits

This test did not try large objects, LFS quotas, concurrent pushes, protected branches, forks, or all Git hosting providers. The GitHub archive check covers the repository archive endpoint, not Releases asset packaging. Source and CI `main` were not changed by the fixture branch.
